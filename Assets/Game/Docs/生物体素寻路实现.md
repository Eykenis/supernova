# 生物体素寻路与行为实现

## 1. 最终行为规则

所有距离都使用体素坐标中的三维直线距离，而不是 Unity 世界单位。当前 Chunk 边长为 32，因此 5 个 Chunk 等于 160 体素。

| 玩家脚部到生物脚部的距离 | 状态 | 行为 |
| --- | --- | --- |
| `distance > 160` | Idle | 立即清除已有路径并停止寻路 |
| `32 < distance <= 160` | Wander | 在半径 32 体素内寻找随机可达目标 |
| `attackDistance < distance <= 32` | Pursue | 以玩家脚下方块为目标寻路 |
| `distance <= attackDistance` | Attack | 清除导航，面向玩家并按攻击前摇/冷却造成伤害 |

`attackDistance` 当前默认 2 体素，但它是序列化参数，可以按生物攻击范围调整。

Wander 使用拒绝采样。每次在以生物为中心、半径 32 体素的圆内选择水平偏移，同时在附近高度中寻找可站立方块；候选必须位于已生成 Chunk 中，并且完整 A* 必须能抵达。最多尝试 16 次，全部失败时进入一个 `wanderRetryInterval` 时长的 Idle，然后才开始下一轮选择。

## 2. 脚部坐标约定

美术 Prefab 的根节点 `(0, 0, 0)` 是生物脚部位置。MeshCollider 可以位于根节点或子节点，烘焙器会把其顶点变换回根节点局部空间，再计算相对于脚部原点的占用格。

路径节点不是“脚部空气格”，而是生物站立的实心支撑方块：

```text
support = 路径节点，必须为实心
foot    = support + (0, 1, 0)
body    = foot + bakedVoxelOffset
```

一个支撑方块可站立，需要同时满足：

1. 支撑方块已生成且为实心。
2. 支撑方块正上方已生成且为空。
3. 把预烘焙体素形状放到 `foot` 后，所有占用格都已生成且为空。

其中形状最底部一层允许接触 Marching Cubes 的地表边界：如果一个底层密度点为实心、
但它正上方的密度点为空，则将其视为脚部和斜面的接触，而不是身体撞入障碍。
更高的身体层仍严格要求为空，未生成数据也仍然拒绝。

任何查询落入未生成 Chunk 都返回不可达。寻路不会把“未知”误当空气，也不会驱动生物走出当前已生成世界。

## 3. MeshCollider 预烘焙工作流

给生物 Prefab 根节点添加 `CreatureVoxelShapeAuthoring`：

1. `Source Collider` 指向代表寻路碰撞形状的 MeshCollider。
2. `Bake Voxel Size` 必须和目标 `MinecraftCaveInfiniteWorld.VoxelSize` 相同。
3. 点击 `Bake Occupied Voxels`。
4. 第一次烘焙选择 `.asset` 保存位置；之后点击同一按钮会更新现有资产。
5. 保持 `Show Occupied Voxels` 开启，Prefab 编辑模式和场景编辑模式都会显示半透明占用格。

烘焙不是简单使用 MeshCollider 的 Bounds：

1. 读取 `MeshCollider.sharedMesh` 的全部三角形。
2. 将顶点从 Collider 局部空间变换到脚部根节点局部空间。
3. 对候选体素执行三角形和 AABB 的 13 轴分离轴相交检测，标记表面体素。
4. 对没有碰到表面的体素中心执行射线奇偶检测，填充闭合网格内部。
5. 把最终的 `Vector3Int` 偏移、边界和烘焙体素尺寸写入 `CreatureVoxelShape` 资产。

模型导入设置必须允许读取网格。如果 Collider 网格不是闭合的，表面格仍会生成，但内部填充结果取决于网格是否具有有效封闭体积。烘焙体素延伸到 `y < 0` 时编辑器会警告，因为这通常表示 Prefab 原点没有放在脚部。

运行时不再读取 MeshCollider 三角形，也不做物理重叠查询；寻路只遍历预烘焙的整数偏移。因此编辑器预览看到的形状和运行时可达检测使用的是同一份数据。

## 4. B 方案：完整累计代价 A*

### 4.1 节点和八邻域

开放集合中的每个节点都是一个可站立的支撑方块。展开节点时，只检查水平面的 8 个邻居：前、后、左、右以及四个对角方向。垂直变化不是额外的展开方向，而是在解析这 8 个水平候选时，通过向下找地面或向上找落脚面得到。

这意味着“每次只展开附近 8 个位置”和“完整 A*”并不冲突。完整性来自搜索会继续展开开放集合中的后续节点，并保留从起点到每个节点的历史代价。

### 4.2 累计代价

对当前节点 `current` 和候选节点 `next`：

```text
tentativeG(next) = bestG(current) + stepCost(current, next)
h(next)           = distance(next, target)
f(next)           = tentativeG(next) + h(next)
```

- `bestG` 保存起点到节点的最低已知累计代价。
- 同一个节点再次被找到时，只有新的 `tentativeG` 更低才会更新。
- 开放集合是按 `f` 排序的最小堆。
- `cameFrom[next] = current` 保存路径来源；到达目标后从目标反向回溯，得到完整路径。

因此历史代价不会在每一帧或每走一步后重置。原文中的“本步代价 + 预测代价”如果只用于选择眼前一步，会退化成贪心最佳优先搜索，遇到障碍可能来回摆动；这里的关键修正是把历史 `g` 明确加入每个候选的 `f`。

### 4.3 单步过渡代价

每个水平候选先查询与当前支撑方块同高的位置：

| 情况 | 处理 | 代价 |
| --- | --- | --- |
| 候选为实心且可站立 | 直接使用 | `1` |
| 候选为空 | 逐格向下寻找第一个实心方块 | 基础 `1`，安全高度内每下降 1 格 `+1`，超出后每格 `+10` |
| 候选为实心但不可站立 | 逐格向上寻找可站立表面 | 基础 `1`，每上升 1 格 `+2` |
| 上升超过 `maximumJumpHeight` | 拒绝 | 不加入开放集合 |
| 单步累计超过 `maximumSingleMoveCost` | 立即停止递归 | 不加入开放集合 |

默认安全下落高度是 3，最大跳跃高度是 1，单步代价上限是 100；三者均可在 Agent Inspector 中配置。

### 4.4 路径重建和物理执行

A* 到达目标后一次性重建从起点到目标的节点列表。生物沿列表移动，每次开始下一段移动前重新调用相同的过渡解析：

- 若目标格仍然可达且解析结果等于路径中的下一节点，则继续移动。
- 若地形、Chunk 可用性或占用情况变化导致验证失败，则立即丢弃路径，后续行为帧重新规划。

运行时把逻辑和物理分为两个组件：

- `CreatureBehaviorAgent` 只读取当前 Transform 对应的逻辑体素、规划路径、推进逻辑节点，
  并提交“水平移动方向、是否上升、指令编号”。它不引用 Rigidbody，不做 Raycast、接地检测，
  也不检查物理层是否正确落在地面上。
- `CreaturePhysicsMotor` 独占非 Kinematic Rigidbody。它在 `FixedUpdate` 中把最新指令转换为
  水平速度、转向和一次跳跃冲量；垂直速度始终由重力和物理碰撞决定。

导航层不会写入 `transform.position`，物理 Motor 也不了解 A*、目标节点或行为状态。

逻辑层每帧只把当前脚部 Transform 映射到体素坐标。映射结果进入下一路径节点，或到节点中心
的三维误差小于 1 个体素时，就认为逻辑上已经到达并发布下一步指令。容差略小于精确的
一格距离，避免站在当前节点时直接跳过相邻节点。

每次重新计算路径前，Agent 都会再次把当前根 Transform 映射为逻辑支撑格，并以此覆盖旧的
逻辑位置和作为 A* 新起点。该同步是物理位置到逻辑坐标的单向采样，不包含接地、碰撞或速度
检查，也不会反向修改 Rigidbody 的位置。

若下一节点高于当前节点，Motor 会为该指令施加一次按上升高度计算的跳跃速度冲量。
下降时不吸附目标高度，而是保持水平引导并让 Rigidbody 自然下落。受击后 Agent 进入 Hurt，
停止导航一小段时间；击退只作为命令交给 Motor，由 Motor 独占 Rigidbody 操作。

Pursue 在玩家脚下目标变化或当前路径完成后重算。Wander 只在没有活动路径时挑选新目标。`maximumExpandedNodes` 默认 8192，用于限制一次同步规划的最坏耗时。

## 4.5 战斗状态机

Player 和 Creature 共用 `CharacterStateMachine<TState>`、`CharacterVitals`、`DamageInfo` 和
`IDamageable`，状态机核心不依赖输入系统、CharacterController、Rigidbody 或寻路查询。

- Player 状态：Idle、Move、Jump、Fall、Attack、Hurt、Dead。左键请求 Attack，命中帧使用球形近战检测并通过 `IDamageable` 发送伤害。
- Creature 状态：Idle、Wander、Pursue、Attack、Hurt、Dead。Wander/Pursue 调用原有 A*；Attack 直接对当前玩家目标发送伤害。
- Player 的物理输出由 `CharacterControllerMotor` 适配器执行；Creature 的速度、跳跃、转向和击退仍只由 `CreaturePhysicsMotor` 执行。
- Hurt 和 Dead 会抢占移动/寻路；Dead 不再接受伤害或发起攻击。

## 5. 场景接入

1. 场景中需要一个已经运行的 `MinecraftCaveInfiniteWorld`。
2. 生物根节点添加 `CreatureVoxelShapeAuthoring`，完成预烘焙。
3. 同一根节点添加 `CreatureBehaviorAgent`。
4. `Cave World` 指向体素世界，`Player Foot` 指向玩家脚部 Transform。
5. 确认烘焙体素尺寸和世界 `VoxelSize` 完全一致。
6. 把生物脚部放在一个实心支撑方块正上方；运行时会在附近 3 格内校正初始支撑节点。

选中运行中的生物时，Scene 视图会显示当前状态颜色、32 体素追击范围以及当前路径。状态可通过 `CurrentState` 读取，路径、目标和最近一次展开节点数也都有只读运行时属性。

## 6. 验证

使用菜单：

```text
Tools > Minecraft Caves > Validate Creature Navigation
```

验证地图会放置一堵两格高墙，要求 A* 从墙旁绕行；同时检查：

- 路径正确包含起点和目标。
- 每一步都属于水平 8 邻域。
- 每一步都能通过执行期过渡复验。
- 单步代价没有超过 100。
- 路径确实离开直线并绕过障碍。

## 7. 示例生物

项目包含可直接使用的示例 Prefab：

```text
Assets/Game/CreatureAssets/ExampleCaveCreature.prefab
```

它遵循脚部原点约定，面向本地 `+Z`，根节点已经带有编辑者配置的 Collider、Rigidbody、
`CreatureVoxelShapeAuthoring`、`CreaturePhysicsMotor` 和 `CreatureBehaviorAgent`。配套形状以
`0.42` 的体素尺寸预烘焙为 16 个占用格。拖入场景后，只需给 Agent 指定 `Cave World` 和 `Player Foot`；
如果目标世界使用其他体素尺寸，需要在 Authoring Inspector 中用相同尺寸重新烘焙。

使用下列菜单可以更新示例的外观材质并补齐缺失的运行时组件：

```text
Tools > Minecraft Caves > Rebuild Example Creature Prefab
```

该构建器不会创建、替换或配置任何 Collider，也不会自动烘焙体素形状。已有 Prefab 上的
CapsuleCollider、BoxCollider 或其他编辑者碰撞配置会原样保留；全新 Prefab 会在没有 Collider
的状态下生成，必须由编辑者在 Prefab 模式中完成碰撞箱和体素形状配置。
