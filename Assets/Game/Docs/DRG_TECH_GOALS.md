# 深岩银河技术借鉴 — 开发目标

把《深岩银河》(Deep Rock Galactic) 四大地形技术拆成可执行的开发目标。每条目标标注优先级与对当前立方体素架构(区块 16×128×16、`ushort` 方块 ID、每区块一 Mesh + MeshCollider、种子重建)的适配结论。

> **前提**:DRG 官方仅公开一篇洞穴生成 devblog,其数据结构/网格化/寻路方案均未官方确认。`[官方]` = 一手确认;`[行业]` = 从 godot_voxel / Recast / Nav3D 等成熟方案推断的实现路径。

优先级:🟢 直接照搬 / 🟡 需改造 / 🔴 方块世界不做。

---

## 模块 1:程序化洞穴生成 —— 🟢 核心借鉴

DRG `[官方]`:"珍珠串项链"——119 个手工房间模板 + 10 biome,隧道串联,模板内二级随机化(同模板可出多变体)。早期试过方块地形后为外观放弃,与生成结构无关。

- [ ] **G1.1 房间模板资产**:定义"房间"为一段体积形状 + 可随机化参数(尺寸/旋转/内部点位)。先做 3~5 个模板跑通。
- [ ] **G1.2 拼接图生成器**:选房间 → 隧道连接 → 校验连通性与不重叠。产物 = `seed + 房间序列`。
- [ ] **G1.3 隧道挖空**:沿路径在方块网格里挖空,出入口用标记点对齐房间。
- [ ] **G1.4 两级种子**:宏观(拼接)一个种子,微观(模板变体)派生子种子,保证确定性 + 兼容现有种子重建存档。
- [ ] **G1.5 biome 参数集**:每 biome 一套方块 ID / 矿脉 / 植被 / 刷怪规则,映射到 `ushort` 查表。

**结论**:迁移成本最低、与方块架构零冲突。优先做这块。

## 模块 2:地形数据结构 —— 🟡 选择性借鉴

`[行业]` godot_voxel 范式:多通道体素(`TYPE`=方块 ID / `SDF`=平滑 / `COLOR`=调色板);均匀区不分配内存;SDF 侧还有截断 + 定点量化。

- [ ] **G2.1 均匀块压缩**:区块整块同值时只存单值 + `is_uniform` 标记,不分配 16×128×16 数组。天空/纯石区省内存显著。🟢 直接可用。
- [ ] **G2.2 方块 ID = TYPE 通道**:现有 `ushort` 已足够,**不引入 SDF 通道**。
- [ ] **G2.3 颜色/材质变体走调色板索引**,而非每体素存 RGBA。
- [ ] SDF 连续梯度存储 / 8-16 位定点量化 🔴 平滑体素专有,方块世界不做。

**结论**:只抄"均匀块压缩"与"调色板索引"两个通用技巧;SDF 整套跳过。

## 模块 3:可破坏地形 / 实时挖掘 —— 🟡 用方块版路径

`[行业]`:平滑路线走 GPU marching cubes(compute shader + GraphicsBuffer 直接访问,免 CPU 回读);方块路线简单得多。⚠️ 被证伪(0-3):"只重算受影响顶点 + 空间剔除"——别抄这个偷懒思路。

- [ ] **G3.1 挖掘 = 改 ID→空气 + dirty 标记 + 局部重建**。永远只重建受影响区块,绝不重建全世界。
- [ ] **G3.2 跨区块边界统一走 `GetBlock`**(越界读空气),保证边界面正确剔除、无接缝。
- [ ] **G3.3 重建单位 = 整个 dirty 区块的 mesh**。方块世界重跑面剔除很快;不做"只更新单面/单顶点"的微优化(收益小、易 bug)。
- [ ] **G3.4 性能兜底(按需)**:卡顿时先把面剔除搬到 Job System + Burst 多线程,最后才考虑 GPU compute。
- [ ] ~~marching cubes / GPU 重网格化~~ 🔴 平滑等值面专用,方块世界不必要。

**结论**:"改 ID + 重建 dirty 区块"即可实时,不上 marching cubes。

## 模块 4:AI 寻路(形变地形上)—— 🟢 重点借鉴工程细节

`[行业]` 两条路线。⚠️ 被证伪(均 0-3):"编辑/流式必须持续全量重烘焙 navmesh"、"运行时烘焙有严重主线程瓶颈"——**都是错的**,局部重建成熟可用,不必悲观。

### A. 地面/爬墙敌人 → 分块 navmesh 局部重建
- [ ] **G4.1 地形 Mesh/Collider 喂给 Recast 类导航**(A* Pathfinding Project 或 NavMeshSurface)。注意 navmesh 是对渲染 Mesh 的**再体素化**,与方块分辨率是两套独立的东西。
- [ ] **G4.2 挖掘后只 re-bake 受影响 tile**(`ReplaceTile` / `NavmeshCut`),不全图重烘焙。
- [ ] **G4.3 navmesh tile 尺寸对齐/整除区块 XZ 尺寸**,使"dirty 区块 → dirty tile"成为简单映射。

### B. 飞行/无重力敌人 → 体积寻路
- [ ] **G4.4 飞行敌人在方块网格上直接做 3D A***(非空气=障碍,空气=通行节点)。方块世界已是均匀体素网格,比引入 SVO 简单。
- [ ] **G4.5 SVO 分层(仅当 3D A* 内存/搜索爆炸时)**:远处合并大节点,参考 Nav3D 的稀疏体素八叉树方案。
- [ ] **G4.6 飞行寻路更新同样只重算受影响 chunk**。

**结论**:核心两点——(a) 理清"MeshCollider→navmesh 再体素化"的两套分辨率;(b) 所有寻路更新走分块局部重建。

## 落地顺序建议

1. **先做模块 1**(洞穴生成)——独立、契合度最高、能立刻看到成果。
2. **模块 3 的 G3.1~G3.3** 你的架构基本已具备,补齐 dirty 区块局部重建即可。
3. **模块 2 的 G2.1** 均匀块压缩,低成本内存优化。
4. **模块 4** 等有敌人需求时再做,按 A(地面)→ B(飞行)顺序。
