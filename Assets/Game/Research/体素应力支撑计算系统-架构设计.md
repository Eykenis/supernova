# 体素应力支撑计算系统 — 架构设计

> 基于论文 *"Graph-Theoretical Description and Continuity Problems for Stress Propagation Through Complex Strut Lattices"* (Reyes-Martinez et al., arXiv:2412.15344) 的 EBC_LB 算法，
> 设计适用于 `MinecraftCaveInfiniteWorld` 体素世界的结构支撑与倒塌检测系统。

---

## 1. 设计目标

当玩家破坏体素时，系统需要回答两个问题：

| 问题 | 输出 |
|------|------|
| **哪些方块需要更新？** | 受影响的局部子图（dirty region），触发重新网格化 |
| **哪些方块缺少支撑、要倒塌？** | "浮动"体素集合（与锚点断开连接的连通分量），标记为倒塌 |

核心约束：
- **不能每破坏一个体素就扫描全图**（O(N²) 不可接受）
- **必须支持增量更新**（只重算受影响区域）
- **必须帧预算可控**（分帧处理大规模倒塌）

---

## 2. 理论基础：从 EBC_LB 到体素支撑图

### 2.1 论文算法的适配

论文研究的是**应力在支柱网络中的传播**。我们的体素世界是论文模型的特例：

| 论文概念 | 体素世界对应 |
|----------|-------------|
| 支柱交汇点 (strut intersection) | 实心体素 |
| 支柱 (strut) | 相邻实心体素之间的连接边 |
| 应力加载边界 (perturbed boundary) | 玩家破坏点 / 重力负载区域顶部 |
| 对面边界 (opposite plane) | 基岩 / 地面锚点 |
| EBC_LB 高值边 | 关键支撑路径——断了就会导致大量体素倒塌 |

### 2.2 关键简化：均匀网格上的 EBC_LB

体素世界是**均匀立方网格**，边长均等。因此：

- **不需要长度加权（EBC_L 退化为 EBC_G）**：所有边权重相同，Dijkstra 退化为 BFS
- **锚点定义明确**：与基岩接触的体素 = 天然锚点
- **支撑方向为垂直向上**：重力方向，支撑从地面向上传播

在此基础上，EBC_LB 的体素版本等价于：

> **从所有锚点出发，到所有其他体素的 BFS 最短路径上各边的被经过次数**

这实际上就是**多源 BFS 边介数中心性**。

### 2.3 支撑度（Support Centrality）定义

对于边 \(e\)（连接体素 A 和体素 B）：

\[
\text{Support}(e) = \sum_{a \in \text{Anchors}} \sum_{v \in \text{Voxels}} \frac{\sigma_{a \to v}(e)}{\sigma_{a \to v}}
\]

其中：
- \(\text{Anchors}\) = 与基岩/地面直接接触的体素集合
- \(\sigma_{a \to v}\) = 从锚点 a 到体素 v 的最短路径总数
- \(\sigma_{a \to v}(e)\) = 这些路径中经过边 e 的数量

**物理含义**：边的支撑度 = "有多少体素依赖这条边获取支撑"。支撑度为 0 的体素 = 浮动体素（无任何锚点可达路径）。

## 3. 算法设计

### 3.1 两级检测策略

我们不直接使用完整 EBC_LB（太贵），而是采用**两级分层策略**：

```
┌─────────────────────────────────────────────────┐
│                Level 1: 连通性检测               │
│  BFS 从锚点出发 → 不可达体素 = 直接倒塌          │
│  复杂度: O(k) （k = 受影响区域体素数）           │
│  触发: 每次体素破坏后立即同步执行                │
├─────────────────────────────────────────────────┤
│                Level 2: 支撑度精算               │
│  EBC_LB 边介数中心性 → 低支撑度体素 = 预警       │
│  复杂度: O(k²) 最坏（但限制在局部子图）          │
│  触发: Level 1 发现连通但支撑路径稀少的区域      │
└─────────────────────────────────────────────────┘
```

### 3.2 Level 1：连通性级联倒塌检测（核心）

这是系统的主力算法，直接回答"哪些方块要倒塌"。

```
算法: DetectCascadingCollapse(removedVoxels)
──────────────────────────────────────────
输入: removedVoxels — 被破坏的体素坐标列表
输出: collapsedVoxels — 应倒塌的体素集合

步骤:
1.  DEFINE affected_region = BFS从破坏点向外扩展，遇到锚点停止
    // 锚点 = Y=0 的实心体素 或 被标记为"结构锚定"的体素
    // 扩展半径 = 32 体素（一个 chunk 宽度），可配置

2.  DEFINE anchors = 受影响区域内所有锚点体素

3.  MULTI_SOURCE_BFS(source=anchors, region=affected_region)
    → 输出 reachable_voxels（所有有支撑路径的体素）

4.  collapsedVoxels = affected_region \ reachable_voxels
    // 从锚点不可达 → 浮动 → 标记为倒塌

5.  FOR each collapsedVoxel:
        ScheduleCollapse(voxel, delay=基于距离的衰减)

6.  REMOVE collapsedVoxels 从体素数据中（设为 Air）

7.  IF collapsedVoxels.Count > 0:
        // 级联：倒塌的体素可能导致更多体素失去支撑
        GOTO 1（以 collapsedVoxels 作为新的 removedVoxels）
        // 但限制迭代次数 ≤ 5（防止无限级联）
```

**关键数据结构**：

```csharp
public struct VoxelSupportState
{
    public bool IsAnchor;           // 是否为锚点体素
    public bool IsReachable;        // 是否从锚点可达（Level 1 结果）
    public float SupportScore;      // 支撑度分数 0-1（Level 2 结果）
    public int SupportPathCount;    // 支撑路径计数（简化的 Level 2）
}
```

### 3.3 Level 2：支撑度精算（预测性预警）

当 Level 1 发现某区域所有体素都"有支撑"但支撑路径稀少时，Level 2 提供预警。

```
算法: ComputeSupportCentrality(region, anchors)
──────────────────────────────────────────
输入: region — 待分析区域（受影响子图）
      anchors — 锚点集合
输出: 每个体素的 SupportScore (0-1)

步骤:
1.  FOR each anchor in anchors:
        Run BFS from anchor through region
        → 记录从该锚点到各体素的所有最短路径
        → 累积每条边的 betweenness

2.  FOR each voxel v in region:
        // v 的支撑度 = 从锚点到 v 的所有路径中最关键边的最小值
        // 直观含义：v 的支撑只和最薄弱的环节一样强
        SupportScore(v) = min(SupportScore(parent(v)), 
                              1.0 / (1.0 + betweenness_rank_of_connecting_edge)))

3.  RETURN SupportScores
```

但实际上对于游戏场景，我们可以用更简单的近似：

**简化支撑度**：体素 v 的支撑度 = 从 v 到最近锚点的不同路径数（取 log 归一化）

```
SimplifiedSupport(v):
    pathCount = CountDisjointPaths(v, nearestAnchor, maxPaths=5)
    return log2(pathCount + 1) / log2(6)  // 归一化到 [0, 1]
    // 0 条路径 = 0.0（应倒塌）
    // 1 条路径 = 0.43（脆弱）
    // 2+ 条路径 = 0.68+（稳定）
```

### 3.4 增量更新：脏区传播

这是区分"哪些方块需要更新"的核心机制。

```
脏区传播规则:
────────────────
破坏发生 → 标记破坏点所在 chunk 为 dirty

对于每个 dirty chunk:
    IF 破坏发生在 chunk 边界附近（≤2 体素到边界）:
        标记相邻 chunk 为 dirty

级联倒塌时:
    倒塌体素所在的 chunk → 标记为 dirty
    倒塌体素传播到相邻 chunk → 标记相邻 chunk 为 dirty
```

这恰好对接到现有的 `CollectMeshesAffectedByVoxel` 机制。

### 4.2 核心类设计

```csharp
// VoxelSupportGraph.cs — 主入口
public class VoxelSupportGraph
{
    // 配置
    VoxelSupportConfig config;

    // 锚点缓存（按 chunk 分块存储，懒加载）
    Dictionary<Vector2Int, HashSet<Vector3Int>> anchorCache;

    // === 公开 API ===

    /// 当体素被破坏时调用
    /// 返回: 需要倒塌的体素列表 + 需要重新网格化的 chunk 列表
    public CollapseResult OnVoxelsRemoved(
        IEnumerable<Vector3Int> removedVoxels,
        IVoxelTerrain terrain
    );

    /// 查询单个体素的支撑状态
    public VoxelSupportState QuerySupport(Vector3Int voxel, IVoxelTerrain terrain);

    /// 标记自定义锚点（如玩家放置的结构支撑柱）
    public void MarkAnchor(Vector3Int voxel);
    public void UnmarkAnchor(Vector3Int voxel);
}

public struct CollapseResult
{
    public List<Vector3Int> CollapsedVoxels;      // 直接倒塌
    public List<Vector3Int> CascadeCollapsed;      // 级联倒塌
    public HashSet<Vector2Int> DirtyChunks;        // 需要重新网格化
    public Dictionary<Vector3Int, float> WeakenedVoxels; // 支撑度下降但未倒塌（用于视觉效果）
}
```

### 4.3 与现有系统的集成点

```
MinecraftCaveInfiniteWorld
│
├── VoxelMining.OnVoxelMined(voxel)
│   └── → VoxelSupportGraph.OnVoxelsRemoved([voxel])
│       ├── 运行 Level 1 连通性检测
│       ├── 输出 collapsedVoxels
│       ├── 调用 terrain.SetVoxel(collapsed, Air)  ← 复用现有 API
│       └── 输出 dirtyChunks → EnqueuePriorityMeshes(chunks)
│
├── 世界加载时
│   └── → VoxelAnchorProvider.BuildAnchorCache(chunk)
│       // 扫描 Y=0 的实心体素，建立初始锚点集合
│
└── 结构放置时
    └── → VoxelSupportGraph.MarkAnchor(structuredVoxel)
        // 玩家放置的结构自动成为锚点
```

## 5. 性能分析

### 5.1 复杂度对比

| 方案 | 最坏时间复杂度 | 空间复杂度 | 适用场景 |
|------|--------------|-----------|---------|
| 全图 BFS | O(N) 所有体素 | O(N) | 不适用— 32×256×32/chunk，N 可达百万 |
| **本方案 Level 1（增量）** | **O(k)**，k = 受影响子图大小 | O(k) | ✅ 单次破坏（k ≈ 100-500） |
| 本方案 Level 2（精算） | O(k²) 最坏，O(k log k) 平均 | O(k) | 可选，大规模破坏时关闭 |
| 论文原始 EBC_LB | O(N^{3/2} log N) | O(N) | 参考基线 |

### 5.2 帧预算分配

```
破坏触发后（同步，主线程）:
├── Level 1 连通性 BFS      ≤ 1ms    (子图 ≤500 体素)
├── 倒塌体素标记 + dirty      ≤ 0.2ms
└── 重新网格化入队             ≤ 0.1ms  (现有机制)

可选后台线程:
└── Level 2 支撑度精算        ≤ 5ms    (Task.Run, 不阻塞主线程)
```

### 5.3 最坏情况保护

| 保护机制 | 阈值 | 行为 |
|----------|------|------|
| 子图扩展半径上限 | 32 体素 | BFS 扩展不可超出此半径 |
| 最大倒塌体素数/帧 | 256 | 超出则分帧处理 |
| 级联迭代上限 | 5 轮 | 超出则下一帧继续（自然错开） |
| 体素总数上限 / 子图 | 4096 (16³) | 超大破坏直接走全图缩略路径 |

## 6. 倒塌行为分级

不是所有失撑体素都应该瞬间掉落。根据支撑度分级处理：

```
SupportScore 分级:
─────────────────
0.0           → Level 1 不可达 → 立即倒塌（重力掉落 + 粒子）
(0.0, 0.3]    → 严重削弱       → 0.3s 延迟倒塌（裂纹预警）
(0.3, 0.6]    → 中度削弱       → 不倒塌，显示微裂纹贴花
(0.6, 0.8]    → 轻微削弱       → 播放细微碎屑粒子
(0.8, 1.0]    → 稳定           → 无变化
```
